# Build FormFlow's next upgrades in this order

FormFlow's biggest client-side gains are mostly cheap engineering, not new models. Four changes give most of the improvement for days of work, not weeks. First, replace the binary 64^3 voxel hull with a hull built from 2D signed distance fields (SDFs), sampled at 128^3 or more in a Web Worker. Second, put a licence-clean learned segmenter in front of the Otsu/Coons pipeline, with a one-click promptable model for corrections. Third, add pinch hysteresis, stroke arming and a grid on the glass plane. Fourth, run MediaPipe in VIDEO mode with a Kalman-predicted ROI fallback, and add a condition monitor that coaches the user. The ambitious options are monocular-depth carving, Teddy-style inflation, auto-generated drawing planes, and an opt-in TripoSR "AI mode". They pay off only once those foundations exist. Licences constrain the choices more than browser feasibility does. The most convenient background-removal package (@imgly) is AGPL. BRIA's RMBG models and the larger Depth Anything V2 variants are non-commercial. Depth Pro and SF3D carry restrictive licences. An all-MIT/Apache stack is available for every area. The notes have one important gap: **almost no browser timings and no FormFlow-specific accuracy numbers.** Every millisecond figure and threshold below is a starting point to measure, not a result. Statements labelled *Inference* are the researchers' engineering judgement, not sourced findings.

## Hand tracking: the palm detector is the weak link, so route around it

MediaPipe's own model card lists low light and motion blur among the conditions that degrade hand tracking ([MediaPipe model card](https://dcmpx.remotevs.com/com/googleapis/storage/SL/mediapipe-assets/Model%20Card%20Hand%20Tracking%20%28Lite_Full%29%20with%20Fairness%20Oct%202021.pdf)). The web hand model itself has not changed in years. That makes the pipeline around it the main lever.

**Run in VIDEO mode, with ROI propagation as the fallback.** The HandLandmarker has two stages: a 192x192 palm detector, then a 224x224 landmark model. In VIDEO/LIVE_STREAM mode it **reuses the previous frame's landmark box and re-runs palm detection only when the hand is lost** ([Hand landmarker guide](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker)). FormFlow's IMAGE-mode zoom-and-follow ROI rebuilds part of that by hand and loses the built-in propagation. *Inference:* run a VIDEO-mode instance on the full frame. When it loses the hand, predict the hand box with a constant-velocity Kalman filter and crop 1.5–2x around the prediction. Then run an IMAGE-mode instance on that crop, upscaled to about 256 px. This bypasses full-frame palm detection, which is the stage that fails under blur and backlight. The existing Pose forearm hint becomes one more measurement in the same filter. The note that `min_tracking_confidence` is an IoU between consecutive boxes, not a classifier score ([guide](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker)), explains why fast motion triggers re-detection even when the hand is clearly visible. FormFlow's lowered threshold already addresses this.

**Upgrade to MediaPipe 1.1.x and use rVFC timing.** v1.1.0 (7 Oct 2026) **exposes per-landmark presence scores in the Web Tasks API**. It also fixes One-Euro drift when the stream resolution changes. v1.1.1 followed on 14 Oct 2026 ([MediaPipe releases](https://github.com/google-ai-edge/mediapipe/releases)). *Inference:* per-landmark presence lets FormFlow freeze only the blurred fingertips while it keeps trusting the wrist and MCP joints. `requestVideoFrameCallback` provides `mediaTime` and `presentedFrames` for every frame ([web.dev](https://web.dev/articles/requestvideoframecallback-rvfc)). *Inference:* those values give real `dt` for One-Euro and Kalman when a dim camera drops to 15–20 fps, and they reveal skipped frames. The researchers also suggest four further changes (*Inference*):

- Replace the 0.35 s hold with about 150 ms of damped rigid extrapolation, shown as a ghosted hand, and never commit strokes from predicted points.
- Accept a re-detection immediately when it falls inside the Kalman gate. Keep the 3-hit rule only for new hands.
- Suppress fist and pinch state changes during fast motion. That is the failure mode behind the existing fist-undo fix.
- Set `numHands: 2`, so a spurious backlit blob cannot take the only slot.

**Treat enhancement as a test-time augmentation, not a permanent filter.** The evidence on enhancement is mixed. GRLib sent several rotated and brightness-adjusted copies of each frame to MediaPipe Hands, and **raised recognition rates over the baseline** on ASL, HaGRID and Kenyan datasets ([arXiv 2310.14919](https://ar5iv.labs.arxiv.org/html/2310.14919)). In ExLPose, however, running LLFlow or LIME enhancement before a body-pose network **made results worse**, because those enhancers optimise perceptual quality rather than the downstream task ([arXiv 2303.15410](https://arxiv.org/pdf/2303.15410)). The notes found no study of CLAHE or gamma against MediaPipe palm detection. *Inference:* gamma or shadow-lift tone curves suit a dark hand in front of a bright window better than FormFlow's linear `brightness()`. A gamma curve lifts the shadows without clipping the highlights, and it costs well under 1 ms in a WebGL2 shader. Pass the shader's canvas straight to `detectForVideo` to avoid `getImageData` round-trips. CLAHE follows a standard per-tile-histogram-plus-bilinear-LUT design ([NVIDIA DALI docs](https://docs.nvidia.com/deeplearning/dali/archives/dali_2_1_1/user-guide/dali_dynamic/operations/nvidia.dali.experimental.dynamic.clahe.html)), but no browser library exists, so it would have to be ported. Skip deblurring entirely.

**Fix exposure at capture, then coach the user.** Chrome on Windows has supported `exposureCompensation` since M60 and `exposureTime` since M76. Most other Image Capture constraints are also supported. `backlightCompensation` is not in the W3C set ([implementation status](https://github.com/w3c/mediacapture-image/blob/main/implementation-status.md)). Support depends on the driver, so feature-detect with `getCapabilities()` ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getCapabilities)). Chrome 114+ exposes OS effects such as `backgroundBlur` as track constraints ([Chrome blog](https://developer.chrome.com/blog/background-blur)). *Inference:* in backlight, set +1 to +2 EV compensation. Request `frameRate: {min: 24–30}` to cap exposure time and therefore blur. Disable OS background blur when it is controllable. For diagnosis, compute variance of the Laplacian, the standard blur score with domain-dependent thresholds ([PyImageSearch](https://pyimagesearch.com/2015/09/07/blur-detection-with-opencv/)), together with mean luma, clipped-highlight fraction and ROI-to-frame luma ratio, on a 160x90 frame. Combine these with the rolling detection rate to show one debounced hint, such as "light behind you" or "move slower". Forum reports that frontal light made tracking reliable ([Cycling '74](https://cycling74.com/ja/forums/n4m-facemesh-handpose-google-mediapipe)) support coaching as a cheap, high-value fix.

**Swapping models is not worth it yet.** TF.js hand-pose-detection wraps the same MediaPipe models. RTMPose-hand via onnxruntime-web's WebGPU EP ([Microsoft blog](https://opensource.microsoft.com/blog/2024/02/29/onnx-runtime-web-unleashes-generative-ai-in-the-browser-using-webgpu/)) has no documented blur robustness and would still need a hand detector. *Inference:* only consider it if logs show the palm detector is the measured bottleneck even after the ROI fallback is in place.

## Segmentation: a learned mask plus one click replaces colour statistics

The current pipeline (Coons patch, Otsu, largest component) fails in exactly the cases where colour statistics fail: clutter, shadows, objects touching the frame, and backgrounds similar in colour to the object. OpenCV.js GrabCut shares that weakness. It also costs **about 6–8 MB of default WASM**, or about 1.5 MB with a custom trimmed build ([OpenCV Q&A](https://answers.opencv.org/question/181963/decreasing-size-of-opencvjs)). The notes found no published browser GrabCut timings. It is best used as a refinement step seeded by a mask, not as the main segmenter.

**Run an automatic salient-object model first.** These models handle clutter and frame contact far better than a border background model. The licence-clean options are ISNet general-use (DIS code is Apache-2.0, [DIS repo](https://github.com/xuebinqin/DIS)), BiRefNet_lite (MIT; **115 MB fp16**; [onnx-community](https://huggingface.co/onnx-community/BiRefNet_lite-ONNX)), and U²-Netp (**4.7 MB**, Apache-2.0, lower quality; [HF](https://huggingface.co/edgetools/u2netp)). The stock 1024 BiRefNet_lite export reportedly fails on onnxruntime-web WebGPU. The 512 and graph-patched re-exports that claim to fix this are self-reported ([runes/birefnet-lite-webgpu](https://huggingface.co/runes/birefnet-lite-webgpu)). Three options are licence traps:

- **@imgly/background-removal 1.7.0 is AGPL.** It is ISNet under the hood, and it needs COOP/COEP headers for full performance ([README](https://cdn.jsdelivr.net/npm/@imgly/background-removal@1.7.0/README.md)).
- **RMBG-1.4 is non-commercial** ([HF](https://huggingface.co/briaai/RMBG-1.4)).
- **RMBG-2.0 is CC BY-NC 4.0** ([GitHub](https://github.com/Bria-AI/RMBG-2.0)).

*Inference:* load ISNet weights directly in onnxruntime-web to keep the quality while avoiding the AGPL wrapper.

**Use a promptable model for corrections.** SlimSAM-77 is Apache-2.0. Quantized, it is an **8.88 MB encoder plus a 4.9 MB decoder** ([HF files](https://huggingface.co/Xenova/slimsam-77-uniform/tree/main/onnx)), and it has an official transformers.js WebGPU demo with positive and negative clicks ([HF Space](https://huggingface.co/spaces/webml-community/segment-anything-webgpu/blob/main/README.md)). The encoder runs once per image, and each click runs only the decoder ([WebSAM](https://xevion.dev/projects/websam)). The MediaPipe Interactive Segmenter (MagicTouch) is lighter at **about 6 MB** and ships in the `@mediapipe/tasks-vision` package FormFlow already uses. It takes positive points or strokes only ([web guide](https://developers.google.com/edge/mediapipe/solutions/vision/interactive_segmenter/web_js); [model card mirror](https://dcmpx.remotevs.com/com/googleapis/storage/SL/mediapipe-assets/Model%20Card%20MagicTouch.pdf)), and the licence for its weights was not found on an official page. SAM 2.1 tiny is about 151 MB, and its video memory is irrelevant for three still photos ([HF](https://huggingface.co/Cr7z676/sam2.1-hiera-tiny-onnx)). *Inference:* MagicTouch is the fastest path for a college demo because it adds no new dependency. SlimSAM is the better tool when negative clicks are needed, for example to remove a shadow.

**Shadows matter more for hulls than for photo editing.** Cast shadows are darker than the background but keep similar chromaticity, which is the standard detection cue ([NSF PAR 10206170](https://par.nsf.gov/servlets/purl/10206170)). Removal from that cue alone is often partial ([Holte et al.](https://vbn.aau.dk/ws/files/19095436/holte_iccv09.pdf)). *Inference:* FormFlow already has a per-pixel background estimate. It can reject masked pixels whose brightness ratio to that estimate falls between 0.4 and 0.95 and whose chromaticity matches it, restricted to the lower part of the bounding box. A mask that is too large produces uncarved "fins". For hulls, prefer slightly eroded masks, threshold soft alpha at 0.5, and skip hole fill for objects with real through-holes.

## Reconstruction: distance fields fix blockiness, depth fixes concavities

**The SDF hull is the single best effort-to-quality trade in the project.** *Inference (no browser benchmarks exist in the notes):*

- Compute a signed 2D distance field per outline once, at about 512^2.
- Define phi(x,y,z) = max(sF, sS, sT).
- Mesh the zero level set with surface nets, using interpolated crossings.

Vertices then land on sub-voxel positions, which removes the blocky steps and the need for the [1 4 1] blur. At 128^3 this costs about 2M max operations, roughly tens of ms in a worker, and a float32 grid takes 8 MB. Liang and Wong's exact voxel-edge intersections for marching cubes are the published counterpart of this idea ([SciTePress](https://www.scitepress.org/Papers/2008/10804)). Exact polyhedral hulls (Franco–Boyer) are well established and watertight ([BMVC 2003](https://bmva-archive.org.uk/bmvc/2003/papers/18/paper018.pdf)), but they target perspective cameras. *Inference:* for three axis-aligned orthographic views, the exact hull is simply the CSG intersection of three extruded prisms. That takes a few lines with manifold-3d. It suits CAD-like input but looks faceted on organic sketches.

**A light post-processing chain finishes the mesh.** *Inference:* Taubin λ/μ smoothing (about 0.5 / −0.53) avoids the shrinkage of plain Laplacian smoothing on thin parts. meshoptimizer's `simplify` and `simplifyWithAttributes` (MIT) handle decimation. Avoid `simplifySloppy`, which ignores topology ([meshoptimizer README](https://github.com/zeux/meshoptimizer/tree/master/js)). manifold-3d (Apache-2.0, WASM; [GitHub](https://github.com/elalish/manifold)) can validate watertightness before STL export, which catches the non-manifold pinch points surface nets can produce.

**Single-view and two-view modes should inflate, not extrude.** Monster Mash showed that sketch-then-inflate gives smooth meshes ready for animation, and its `src` code is Apache-2.0 ([google/monster-mash](https://github.com/google/monster-mash)). *Inference:* the same 2D SDF d gives a Teddy-style height h = sqrt(2Rd − d²). Feeding phi = |z| − h through the existing surface-nets path yields a watertight result. Intersecting inflated views gives rounded edges instead of boxy prism intersections. A lathe along a user-drawn spine extends revolution to horns, handles and tails.

**Concavities need a second signal, and only photos provide one.** Depth Anything V2 Small is **Apache-2.0 and 19.1–27 MB quantised**. Its Base, Large and Giant siblings are **CC-BY-NC-4.0** ([model card](https://huggingface.co/onnx-community/depth-anything-v2-small); [files](https://huggingface.co/onnx-community/depth-anything-v2-small/tree/main/onnx)), and it runs in real time in a transformers.js WebGPU demo ([Xenova Space](https://huggingface.co/spaces/Xenova/webgpu-realtime-depth-estimation/blob/main/index.html)). *Inference:* fit scale and shift of the relative depth to the hull near the silhouette rim, then carve with max(phi_hull, z_front − z). This recovers concavities that face the camera, such as a bowl seen from above, but not hidden ones, and it fails on line art. Depth Pro weighs about 0.6 GB at q4 and has conflicting Apple licence metadata ([DepthPro-ONNX](https://huggingface.co/onnx-community/DepthPro-ONNX)), so treat it as non-commercial. For full image-to-3D, **TripoSR is the only permissive model that runs fully in-browser.** It is MIT, with a 485 MB int8 file on WebGPU. It needs the subject cut out at 0.85 of the frame width on mid-grey, because a white background creates phantom geometry ([cgb/triposr-onnx-webgpu](https://huggingface.co/cgb/triposr-onnx-webgpu)). SF3D uses the Stability Community Licence ([needle-tools](https://huggingface.co/needle-tools/SF3D-webgpu)). Hunyuan3D 2.1 excludes the EU, UK and South Korea ([LICENSE](https://huggingface.co/tencent/Hunyuan3D-2/blob/main/LICENSE)). TRELLIS.2 needs a server GPU.

## Interaction: planes, grids and hysteresis beat free depth

The strongest evidence in the notes comes from Arora et al. (CHI 2017):

- A physical surface improved accuracy by **22%** over unguided mid-air drawing, and a *virtual* surface by up to **17%**.
- **Grids improved accuracy by 17% and scaffolding curves by 57%.**
- Tracing over curves hurt aesthetics, and drawn circles failed to close because of poor depth perception.
- Designers wanted to switch between freeform and controlled modes.

([Arora et al. 2017](https://research.autodesk.com/app/uploads/2023/03/experimental-evaluation-of-sketching.pdf_recSPFZ4RbLaE2Uio.pdf))

FormFlow's glass plane already follows this principle. A grid on it is the cheapest evidence-backed addition. Multiplanes generates snapping planes and beautification triggers from previous strokes ([SFU](https://vvise.iat.sfu.ca/pubs/machuca2018multiplanes)). Smart3DGuides improved shape-likeness with guides that do not constrain the stroke ([Adobe Research](https://research.adobe.com/publication/smart3dguides-making-unconstrained-immersive-3d-drawing-more-accurate)). One caveat applies to all of these results: every study cited used HMDs with 6-DoF controllers, not a monitor and a webcam.

**Depth should come from plane selection, not from MediaPipe z.** MediaPipe's normalised z is relative to the wrist, and its world landmarks are centred on the hand ([web guide](https://developers.google.com/edge/mediapipe/solutions/vision/hand_landmarker/web_js)), so neither is camera distance. Monocular push/pull from changes in apparent hand scale is feasible: Fujitsu claims about 90% detection, but that is a vendor figure ([MVA 2013](https://www.mva-org.jp/Proceedings/2013USB/papers/09-11.pdf); [press release](https://info.archives.global.fujitsu/global/about/resources/news/press-releases/2013/0520-01.html)). *Inference:* use rigid-landmark scale (wrist to index MCP, plus index MCP to pinky MCP) only as a clutched, relative push/pull control on the plane, or use an off-hand slider. Add PCA-fitted auto-planes from finished strokes and a side-view depth inset.

**Pinch reliability is solved practice in industry.** Ultraleap uses an activation threshold of about 0.8 with a lower release value, which is hysteresis ([Ultraleap](https://docs.ultraleap.com/xr-and-tabletop/xr/unity/plugin/features/pinch-and-grab-detection.html)). Meta recommends a clean thumb–index pinch and warns that grabs with several fingers curled reduce tracking accuracy. It also recommends audio and visual confirmation in place of haptics and only a few gestures ([Meta](https://developers.meta.com/vr/design/hands-best-practices/)). That guidance argues against FormFlow's thumb+middle grab and peace-sign pan. *Inference:* normalise pinch distance by |wrist − middle MCP|, engage below about 0.25, and release above about 0.4. Arm strokes only after 100–150 ms or a minimum travel, and discard very short strokes. Show a shrinking proximity ring and a click sound.

**Fatigue and beautification.** Elbow-anchored input supports comfortable seated interaction ([Veras et al. CHI 2021](https://hci.cs.umanitoba.ca/publications/details/elbow-anchored-interaction-designing-restful-mid-air-input)). Offset techniques such as ProxyHand reduced Consumed Endurance, a measure of arm fatigue, but departing further from 1:1 mapping reduced presence ([KIT](https://hci.iar.kit.edu/559.php)). *Inference:* presence matters less on a monitor than in VR, so map a small comfortable "elbow on desk" box to the full canvas, with clutching and speed-dependent gain. For beautification, the 1€ filter's authors suggest starting at mincutoff ≈ 1 Hz and tuning beta first ([Casiez](https://cristal.univ-lille.fr/~casiez/1euro)). $P is BSD-licensed JavaScript for symbol and command gestures ([$P](https://depts.washington.edu/acelab/proj/dollar/pdollar.html)). *Inference:* geometric line and circle fits plus endpoint snapping work better for primitives, and they directly fix the circle-closure failure Arora observed. Apply them only in controlled mode, and keep the raw stroke so the user can undo.

**Evaluation.** A within-subjects study comparing the baseline with each improvement is consistent with the precedents: KIT used 21 participants with CE and workload, and Arora measured error against target curves ([KIT](https://hci.iar.kit.edu/559.php); [Arora](https://research.autodesk.com/app/uploads/2023/03/experimental-evaluation-of-sketching.pdf_recSPFZ4RbLaE2Uio.pdf)). Measure five things: time, in-plane and depth error separately, accidental strokes (undone within 2 s), SUS, and raw TLX. SUS scores are not percentages, and the 68 average comes from later aggregation, not Brooke ([MeasuringU](https://www.measuringu.com/sus/)). The researchers' suggested 8–16 participants is an inference; no source specified a sample size.

## Prioritised roadmap

Effort scale: S = one day or less, M = a few days, L = a week or more. Ordering follows benefit per effort and dependencies. The SDF field, segmentation masks and logging all feed later items. Library versions and licences come from `npm view` on 2026-10-29 ([reconstruction notes' npm sources](https://www.npmjs.com/package/manifold-3d)) or from the model pages cited above. For @mediapipe/tasks-vision, "1.1.x" refers to the MediaPipe repo release; the npm version was not checked separately. **Flags:** ⚠AGPL, ⚠NC (non-commercial), ⚠? (licence unverified).

## Conclusion

The notes point to one shared design choice across all four areas: **make FormFlow's intermediate representations continuous.** That means signed distance fields instead of binary voxels, soft masks instead of Otsu bitmaps, predicted boxes instead of a fixed hold, and pinch distances with hysteresis instead of a single threshold. The 2D SDF matters most. Once it exists it serves the smooth hull, Teddy inflation, depth carving and the TripoSR intersection, so it should be built before anything else in reconstruction.

The main open risk is unmeasured browser performance, more than any missing model. No source gives Chrome WebGPU timings for SlimSAM, ISNet, Depth Anything or TripoSR, or any MediaPipe accuracy under blur. The highest-value first task is therefore the logging and replay harness. It turns every "inference" in this report into a number FormFlow can defend in its write-up. All of the cited interaction evidence comes from VR, so a desktop-webcam study would itself be a novel contribution.
